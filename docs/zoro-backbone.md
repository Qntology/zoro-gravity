# zoro 백본 순전파

Zoro-1 의 텍스트 백본을 `core/src/ai/zoro/` 에 직접 구현했습니다. 다른 구현을 가져오거나 외부 모델 코드를 쓰지 않았고, 구조는 `models/zoro` 의 `config.json` 과 가중치 텐서의 이름 · 모양에서 읽었습니다.
logis-center 는 가중치를 올리고 내리는 **최적화 방식**만 참고했습니다 ([weight-residency.md](weight-residency.md)).

쓰임은 둘입니다. **판단**은 프리필 한 번으로 최종 은닉 상태를 얻어 `jev_head` 에 넘깁니다 (0-Generation). **글쓰기**는 층별 상태를 이어 가며 토큰을 하나씩 만듭니다 (아래 "글쓰기" 절).
비전 타워(이미지 입력)는 두 경로 모두 텍스트뿐이라 구현하지 않았습니다. 비전 가중치는 `mmproj-zoro-bf16.gguf` 에 따로 있습니다 ([model-quantization.md](model-quantization.md)).

## 구조

config 에서 읽은 값: 층 32개, hidden 2560, 어휘 248078, RMSNorm eps 1e-6, 임베딩 · 출력 투영 공유.

```
토큰 → 임베딩 행 조회 (표를 올리지 않고 파일에서 필요한 행만)
 └ 블록 ×32 (선형 주의 3개, 전체 주의 1개가 반복. 전체 주의는 3, 7, 11, … 31 번째)
     x → RMSNorm(attn_norm) → 토큰 섞기 → + x
       → RMSNorm(post_attention_norm) → SwiGLU MLP (9216) → + x
 └ RMSNorm(output_norm) → 은닉 상태 [토큰, 2560]
```

**RMSNorm**: `x / sqrt(mean(x²) + eps) × (1 + w)`. 디코더의 정규화 가중치(`attn_norm`, `post_attention_norm`, `q_norm`, `k_norm`, `output_norm`)는 0 근처에서 시작하는 형태라서 올릴 때 1 을 더해 둡니다.
선형 주의 안의 게이트 정규화(`ssm_norm`)는 평균이 0.92 인 일반 형태라 가중치를 그대로 곱합니다. 가중치 통계로 가렸고 (`weight_groups` 예제), 실제 다음 토큰이 말이 되는 것으로 확인했습니다.

### 전체 주의 층 (8개)

- `attn_q` [8192, 2560] 의 출력은 헤드마다 `[질의 256 | 출력 게이트 256]` 입니다. 질의 헤드 16개, KV 헤드 4개 (GQA), head_dim 256.
- 질의 · 키는 헤드별 RMSNorm(`attn_q_norm`, `attn_k_norm`) 뒤에 RoPE 를 적용합니다. 앞 64차원(`partial_rotary_factor` 0.25)만 반으로 나눠 회전하고 나머지 192차원은 그대로입니다. θ = 10⁷.
- 텍스트만 다루므로 세 위치축(시간 · 높이 · 너비)이 같아서 `mrope_section [11,11,10]` 은 일반 RoPE 와 같은 결과입니다.
- 점수 = `q·k / sqrt(256)`, 인과 마스크, softmax. 질의를 512개씩 나눠 계산해서 점수 행렬 크기를 묶습니다.
- 출력 = `o_proj(주의 출력 × sigmoid(게이트))`.

### 선형 주의 층 (24개, 게이트 델타 규칙)

- 입력 투영 4개: `attn_qkv` [8192] (q 2048 + k 2048 + v 4096), `attn_gate` [4096] (z), `ssm_beta` [32], `ssm_alpha` [32].
- q · k · v 채널에 깊이별 인과 컨볼루션(폭 4) + SiLU.
- q · k 를 L2 정규화하고 q 에 1/√128 을 곱합니다. 키 헤드 16개, 값 헤드 32개 (값 헤드 h 는 키 헤드 h/2 를 읽음).
- 게이트: `β = σ(beta)`, `g = −exp(A_log) · softplus(alpha + dt_bias)`.
- 값 헤드마다 상태 S [128, 128] 를 토큰 순서대로 갱신합니다: `S ← exp(g)·S`, `Δ = β·(v − Sᵀk)`, `S ← S + k Δᵀ`, `o = Sᵀq`.
- `o` 에 헤드별 게이트 RMSNorm(`ssm_norm`)과 `SiLU(z)` 를 곱하고 `ssm_out` 으로 hidden 에 되돌립니다.
- 이 핵심(컨볼루션 · 순환 · 게이트 정규화)은 포크의 `candle_core::delta_rule` 연산을 씁니다. ROCm 은 GPU 커널(처음 쓰기 전에 CPU 와 비교해 맞을 때만 사용)이고, 독립 GPU 의 Vulkan 에는 커널이 없어서 입력을 CPU 로 내려 CPU 커널로 계산한 뒤 결과만 올립니다.

## 확인한 것과 방법

| 확인 | 방법 | 결과 |
| --- | --- | --- |
| 연산 구현이 정의대로인가 | 텐서 연산 없는 스칼라(f64) 기준 구현과 비교. 작은 합성 모델(선형 3 + 전체 1) | 상대오차 < 1e-4 |
| 개별 연산 | RMSNorm · RoPE · 인과 주의(질의 구간 1 · 3 · 7 · 512) · 게이트 델타 규칙을 각각 스칼라 구현과 비교 | 통과 |
| 인과성 | 마지막 토큰만 바꿔도 앞 토큰의 은닉 상태가 비트 단위로 같음 (선형 · 전체 주의 모두) | 통과 |
| 구조 가정 (정규화 방식, 출력 게이트, RoPE, 선형 주의) | **실제 q8 가중치**로 "The capital of France is" 의 다음 토큰 | `" Paris"` 37 ~ 39% 1위, 이어서 "." · `<think>` 등 자연스러운 문장 |
| 백엔드 일치 | 같은 프롬프트의 다음 토큰 확률 | CPU 38.9% · Vulkan 37.3% · ROCm 37.3% (CPU 만 활성값도 양자화) |
| 프롬프트 위치 | 실제 토크나이저로 20개 코드 전부 | 선택지 위치까지 읽은 글이 정확히 그 코드로 끝남 |
| 스트리밍 = 상주 | 블록 8개씩 4구간 대 전체 상주 | 판단 확률 차이 1e-4 이하 |
| GPU = CPU | 같은 판단 | 확률 차이 0.0014 이하, 선택 같음 |

기준 구현은 **내가 같은 이해로** 쓴 것이라 구현 실수(모양 · 인덱스 · 연산 순서)를 잡을 뿐 구조 이해가 맞는지는 말해 주지 않습니다. 이해가 맞는지는 실제 가중치의 다음 토큰으로만 확인했습니다.
이 PC 에는 원본 구현(PyTorch)이 없어서 층 단위로 숫자를 대조하지는 못했습니다.

## 실측 (zoro q8, 판단 프롬프트 149 토큰, 호출 한 번)

| 백엔드 | 첫 호출 (가중치 적재 포함) | 이후 호출 | 선형 주의 24층 | 전체 주의 8층 |
| --- | --- | --- | --- | --- |
| ROCm (RX 6600) | 3.3 s (적재 2.2 s) | **0.67 s** | 0.50 s | 0.17 s |
| Vulkan (RX 6600) | 5.2 ~ 5.7 s (적재 3.3 s) | 1.5 ~ 1.7 s | 1.33 s | 0.32 s |
| CPU (Ryzen 5 5600X) | 약 100 s | 약 100 s | 74 s | 24 s |

`ZOROGRAVITY_ZORO_PROFILE=1` 로 잰 값입니다 (층마다 장치 작업을 기다려서 전체보다 약간 느림). [gpu-backends.md](gpu-backends.md) 3.6절의 변경 전 값이고, 지금은 첫 호출 · 이후 호출이 ROCm 3.1 s · 0.62 s, Vulkan 3.7 s · 1.3 s 입니다. 프롬프트가 5토큰이면 ROCm · Vulkan 모두 0.2 ~ 0.3 s 입니다.

- 시간은 대부분 Q8_0 행렬곱입니다 (층마다 MLP 3개와 투영). Vulkan 의 선형 주의 층은 CPU 로 도는 델타 규칙이 층당 약 14 ms 를 더합니다.
- CPU 는 폴백용입니다. 판단 한 번에 100 s 라서 실사용 대상이 아닙니다.
- 속도를 더 줄이는 길 (아직 안 함): 공통 앞부분(시스템 지시문 · 규칙)의 상태를 캐시하는 접두 캐시, Vulkan 델타 규칙 커널.

## 글쓰기

토큰을 하나씩 만드는 경로입니다 (`ZoroModel::generate`, `ZoroBackbone::write`). 층마다 상태를 이어 갑니다.

| 층 | 이어 가는 상태 |
| --- | --- |
| 전체 주의 8개 | 키 · 값 캐시 (`LayerCache`) |
| 선형 주의 24개 | 합성곱 상태와 순환 상태 (`GdnState`) |

- 출력 투영은 임베딩 표입니다 (`tie_word_embeddings`). 글을 쓸 때만 표를 올립니다. 판단 경로는 표를 올리지 않습니다.
- 모든 블록이 한자리에 있어야 해서 스트리밍 없이 상주합니다. 예산이 모자라면 오류입니다.
- 가장 확률이 높은 토큰만 고르므로 같은 입력이면 같은 글이 나옵니다.
- 시험 `generating_with_state_writes_the_same_tokens_as_rereading_every_time` 이 상태를 이어 쓴 결과와 매번 전체를 다시 읽은 결과가 같음을 확인합니다.
- ROCm 토큰당 30 ms 입니다 (아래 자기 추측 디코딩. 캐시 없이 매번 다시 읽을 때 0.5 s).

모델이 쓴 글의 쓰임과 검사는 [automation-mode.md](automation-mode.md) 10절에 있습니다.

## 자기 추측 디코딩

같은 가중치로 앞 토큰을 내다보고 자기회귀로 검증합니다 (`ai::speculative`, `decode_stream`). 이 모델은 블록 디퓨전으로 학습됐습니다. `block_diffusion.json` 에 `bd_size` 8, 마스크 토큰 248077 (`<|mask|>`, 어휘의 마지막 자리) 이 있고, 변환할 때 텍스트 GGUF 메타데이터(`zorogravity.block_diffusion.*`)로도 옮깁니다. 초안은 언어 가중치만 쓰므로 비전 타워(mmproj)와 관계가 없고 올리는 묶음도 그대로입니다.

순전파 하나에 `[검증할 토큰, 후보 …, 마스크 …]` 를 싣습니다.

- 인과 주의에서는 행의 출력이 그 행까지의 입력에만 달려 있습니다. 뒤에 마스크가 붙어도 앞쪽 행은 자기회귀 값 그대로입니다 (시험 `a_row_does_not_depend_on_the_masks_after_it`).
- 후보는 왼쪽부터 자기회귀 예측과 일치하는 만큼만 채택합니다. 모든 토큰을 검증하므로 추측의 양과 상관없이 글이 같습니다.
- 후보를 모두 채택하면 마스크 행의 출력이 다음 순전파의 후보가 됩니다. 후보가 없으면 문맥에서 끝 두 토큰이 마지막으로 나온 자리를 찾아 그 뒤 토큰을 가져옵니다 (요약은 원문의 표현을 옮겨 적는 일이 많습니다).
- 앞부분만 채택하면 전체 주의는 키 · 값을 잘라 넣습니다. 선형 주의의 순환 상태는 자를 수 없어서, 들고 있던 입력으로 그 자리까지 다시 계산합니다 (순전파마다 약 2 ms).
- 글쓰기에는 조기 종료가 없습니다. 공문서에 들어갈 글이라 모든 토큰을 검증합니다.

기본값은 장치마다 다릅니다. 잰 장치에서만 추측합니다.

| 장치 | 마스크-탐색-폭 | 이유 |
| --- | --- | --- |
| ROCm | 2-2-3 | 3행까지는 순전파 비용이 조금만 늘어납니다 |
| Vulkan | 0-2-3 | 다중 행 커널이 없어서 마스크가 손해입니다 (아래 표) |
| CUDA · CPU | 0-0-0 | 재지 않았습니다 |

`ZOROGRAVITY_ZORO_SPECULATION=마스크:탐색:폭` 으로 바꿀 수 있습니다. 블록 디퓨전 설정이 없는 파일은 마스크를 쓰지 않습니다.

### 토큰당 시간 (ROCm, 실제 프롬프트 14개 · 483 토큰, 글은 모두 같음)

| 단계 | 토큰당 | 프리필 |
| --- | --- | --- |
| 처음 (한 토큰씩) | 77.5 ms | 1.2 s |
| Q8_0 다중 행 커널 (포크) | 42 ms | 1.2 s |
| 버퍼 캐시 1 GiB | 35.7 ms | 0.96 s |
| **자기 추측 (마스크 2 · 탐색 2 · 폭 3)** | **30.2 ms** | 0.96 s |

가장 큰 이득은 추측이 아니라 커널과 버퍼 캐시입니다. 자기 추측을 재다가 찾은 병목입니다 ([gpu-backends.md](gpu-backends.md) 3.6절).

### 추측의 양 (같은 조건)

| 마스크-탐색-폭 | 토큰당 | 순전파 | 패스당 토큰 | 후보 채택 |
| --- | --- | --- | --- | --- |
| 0-0-0 (자기회귀) | 35.6 ms | 483 | 1.00 | - |
| 0-2-3 | 29.5 ms | 342 | 1.41 | 54.0% |
| 1-0-3 | 32.3 ms | 310 | 1.56 | 74.6% |
| 2-0-3 | 32.0 ms | 299 | 1.62 | 65.0% |
| 1-2-3 | 31.6 ms | 303 | 1.59 | 71.4% |
| **2-2-3** | **30.1 ms** | 281 | 1.72 | 59.9% |
| 2-0-0 (폭 제한 없음) | 48.3 ms | 269 | 1.80 | 62.8% |
| 0-4-0 (폭 제한 없음) | 41.2 ms | 328 | 1.47 | 33.3% |

0-2-3 과 2-2-3 은 차이가 오차 수준입니다. 문맥 탐색은 원문을 옮겨 쓸 때만 듣고 마스크는 어떤 글에서나 동작해서 2-2-3 을 골랐습니다. 이 14개는 고를 때 본 글이므로 다른 글에서는 달라질 수 있습니다.

Vulkan 은 같은 글에서 자기회귀 80.0 ms, 0-2-3 74.9 ms, 2-2-3 88.1 ms, 1-0-3 98.8 ms 입니다. 글은 여기서도 14개 모두 같습니다.

모든 설정에서 글이 같았지만 수학적으로 보장되는 것은 아닙니다. 한 행씩 읽을 때와 여러 행을 읽을 때 부동소수점 반올림이 달라서, 1등과 2등이 거의 같은 자리에서는 다른 토큰을 고를 수 있습니다. 재현은 같은 설정 안에서 보장됩니다.

폭을 3 으로 묶은 이유는 순전파 비용이 고르게 늘지 않고 계단처럼 뛰기 때문입니다. 층 · 어휘 투영 · 전송 · top-1 을 합한 ms 입니다.

| 행 수 | 1 | 2 | 3 | 4 | 5 | 6 ~ 10 | 11 ~ 13 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 순전파 | 36 | 46 | 53 | 70 | 108 | 107 ~ 125 | 199 ~ 215 |

5행과 11행의 계단은 Q8_0 커널 안에서 생깁니다. 임시 합을 없애 레지스터를 줄여도 그대로라서 원인은 밝히지 못했습니다.

### 블록 초안을 따로 돌리지 않는 이유

처음에는 gocr 처럼 `[다음 토큰, 마스크 × 7]` 을 블록 주의로 한 번, 검증을 인과 주의로 한 번 돌렸습니다. 글은 같았지만 느렸습니다 (블록 8: 토큰당 210 ms, 자기회귀 77.5 ms).

초안의 위치별 정확도 (앞 자리가 모두 맞았을 때의 조건부, 블록 8):

| 위치 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 블록 주의 | 98.3% | 70.5% | 72.7% | 66.1% | 83.8% | 82.8% | 78.3% |
| 인과 주의 | 100% | 67.2% | 70.7% | 66.0% | 91.4% | 83.9% | 68.0% |

- 채택한 토큰이 363개와 362개로 같습니다. 이 모델에서는 블록 주의의 이득이 없어서 초안과 검증을 한 순전파로 합쳤습니다.
- 블록당 약 3 토큰이 맞습니다. 둘째 자리부터 바로 앞 토큰을 모른 채 맞혀야 해서 정확도가 70% 로 떨어집니다. 그래서 순전파 두 번에 4 토큰을 얻는 구조로는 자기회귀를 넘기 어렵습니다.
- 명세의 Block Diffusion 16 tokens/step 과 달리 이 모델의 블록은 8 입니다. 명세의 250 ms 는 나오지 않습니다 (35 토큰 요약에 프리필 0.96 s + 쓰기 1.1 s).

## 한계와 가정

1. **마스크**: 판단은 인과 마스크(왼쪽 토큰만 봄)를 씁니다. 이 모델은 블록 디퓨전(`bd_size` 8)으로 학습됐는데, `jev_head` 를 어떤 마스크로 학습했는지는 알 수 없습니다. 다음 토큰 예측이 정상인 것은 확인했습니다.
2. **은닉 상태 위치**: 최종 RMSNorm 이후의 값을 `jev_head` 에 넣습니다. 정규화 이전일 가능성은 배제하지 못했습니다 ([jev-head.md](jev-head.md) 6절).
3. **길이**: 한 번에 8192 토큰까지 받습니다. 시험한 프롬프트는 최대 150 토큰 정도이고, 긴 문맥에서의 수치는 확인하지 않았습니다.
4. **정밀도**: q8 양자화 후의 로짓 품질을 정량 평가하지 않았습니다 (다음 토큰이 상식적인 것만 확인). 정밀도 점검은 층 출력 오차의 프록시입니다 ([model-quantization.md](model-quantization.md)).
5. **판단과 글쓰기는 상태를 나누지 않습니다.** 판단은 호출마다 프롬프트 전체를 다시 계산합니다. 명세의 "판단 때 만든 KV 캐시 재사용"은 하지 않습니다. 두 프롬프트의 지시문이 달라 겹치는 앞부분이 거의 없기 때문입니다.
6. **NaN 방어**: 선택한 은닉 상태에 NaN · 무한대가 있으면 판단하지 않고 오류를 냅니다 (`rows_to_host`).
7. **재현성**: 같은 프로세스에서 같은 질문은 비트 단위로 같고, GPU 에 가중치가 모두 올라간 상태에서는 프로세스 사이에도 같았습니다 (Vulkan 8번 반복). 장치 메모리가 모자라 일부 가중치가 호스트에 남으면 달라지므로 `Residency` 가 그런 적재를 거부합니다 ([weight-residency.md](weight-residency.md)). CPU 와 GPU 사이에는 활성값 양자화 때문에 약 1% 포인트 차이가 있습니다.
8. **CPU 경로의 양자화 오차**: CPU 의 Q8_0 행렬곱은 활성값도 8비트로 줄입니다. 선택은 같지만 확률이 중간값이면 GPU 경로와 6.5% 포인트까지 다릅니다 (2홉 질문 0.746 / 0.681). 자동화 기준 0.95 는 GPU 경로에서 맞춘 값이라 CPU 경로의 확신도에 그대로 쓰면 안 됩니다.

## 코드 구조

| 파일 | 역할 |
| --- | --- |
| `ai/zoro/config.rs` | GGUF 메타데이터에서 구조 값을 읽고 검증 (`layer_types` 는 원본 config 에서) |
| `ai/zoro/ops.rs` | 게이트 델타 규칙과 그 상태. 장치 커널은 CPU 기준과 비교해 맞을 때만 씀 |
| `ai/zoro/model.rs` | 올릴 때 변환(`prepare`), 단계 계획(상주 / 스트리밍), 층 순전파, 상태를 이어 가는 글쓰기, 텐서 모양 검증 |
| `ai/tokenizer.rs` | 프롬프트 바이트 위치 → 토큰 번호 (`tokenizers`, Qwen2 방식 BPE). gocr 와 함께 씁니다 |
| `ai/zoro/mod.rs` | `ZoroBackbone` (`Backbone` · `TextWriter` 구현), `open_decision_model` (`jev_head` 와 결합) |
| `ai/zoro/reference.rs` | 시험 전용 스칼라 기준 구현과 합성 모델 생성기 |

사용:

```rust
let residency = Residency::shared(device.clone(), Budget::auto(&device));
let model = zorogravity_core::ai::zoro::open_decision_model(Path::new("models/zoro"), residency)?; // PointerModel
let engine = Engine::new(salt, policy, Some(Box::new(model)));
```

점검 예제: `zoro_probe`(다음 토큰), `decide_probe`(판단 경로 전체), `write_eval`(글쓰기), `residency_check`(올리고 내리기), `weight_groups`(묶음 크기와 가중치 통계).
