# 가중치 상주 관리 (모델은 한 번에 하나, 단계마다 필요한 묶음만)

RX 6600 은 VRAM 이 8 GB 입니다. zoro q8 은 5.15 GB, gocr q8 은 1.58 GB 라서 둘을 통째로 올리면 빠듯하고, 모델 하나도 통째로 올릴 이유가 없습니다.
그래서 이 엔진은 다음 규칙을 코드로 지킵니다 (`core/src/ai/residency.rs`).

1. **모델은 한 번에 하나만 올라옵니다.** 다른 모델의 가중치를 올리기 전에 이전 모델을 모두 내립니다.
2. **모델 안에서도 지금 단계가 쓰는 묶음만 올립니다.** 단계가 끝나 쓰지 않는 묶음은 다음 단계로 넘어가면서 내립니다.
3. **내린 메모리는 실제로 돌려받습니다.** 동기화 → 작업 버퍼 반환 → 메모리 풀 반환 순서로 비우고, 전후의 장치 여유 메모리를 기록합니다.
4. **쓰는 중인 묶음은 내릴 수 없습니다.** 핸들(`Arc<Loaded>`)을 쥔 채로 내리려 하면 오류입니다. "내렸다고 기록했는데 메모리가 남는" 일을 막습니다.

방식은 logis-center 의 단계 전환(`unload_generation_slots` → 쓰는 타워만 올림 → 즉시 반환 → `settle_gpu_memory`)을 참고했고, 코드는 가져오지 않았습니다.

## 묶음과 단계

| 묶음 (`Group`) | 담는 텐서 | 비고 |
| --- | --- | --- |
| `Vision` | `model.visual.*` | 이미지를 읽을 때만 |
| `Embedding` | `token_embd.weight` | 표 전체. zoro 판단은 올리지 않고 **필요한 행만 파일에서 읽습니다** |
| `Blocks{start,end}` | `blk.N.*` (N 은 구간 안) | 텍스트 블록. 구간 단위로 올림 · 내림 |
| `Output` | `output_norm.weight`, `output.weight` (있으면) | zoro 는 `output.weight` 가 없음 (임베딩과 공유) |

**단계(`Phase`)** 는 "지금 필요한 묶음의 전체 목록"입니다. `Residency::enter(모델, 단계)` 가 ① 다른 모델이면 통째로 내리고 ② 단계에 없는 묶음을 내리고 ③ 없는 묶음만 올립니다. 이미 올라온 묶음은 다시 읽지 않습니다.

### zoro 판단 경로 (텍스트 전용)

| 가중치 | 올림? | 이유 |
| --- | --- | --- |
| 텍스트 블록 32개 | 예 (3631 MB) | 순전파 |
| 출력 정규화 | 예 (10 KB) | 최종 은닉 상태 |
| 토큰 임베딩 표 (643 MB) | **아니오** | 프롬프트의 토큰 행(수백 개)만 파일에서 읽음 |
| 비전 타워 (636 MB BF16) | **아니오** | 판단 입력은 텍스트뿐. `mmproj-zoro-bf16.gguf` 에 따로 있고 읽지 않음 |
| 출력 투영 (lm_head) | **아니오** | 임베딩과 공유이고, 포인터 판단은 어휘 확률을 쓰지 않음 |
| `jev_head` (5.2 MB, F32) | CPU | 장치에 올릴 만큼 크지 않음 |

### zoro 글쓰기 경로

| 가중치 | 올림? | 이유 |
| --- | --- | --- |
| 텍스트 블록 32개 | 예 (3631 MB) | 토큰마다 모든 블록을 지나므로 스트리밍하지 않음 |
| 출력 정규화 | 예 (10 KB) | 최종 은닉 상태 |
| 토큰 임베딩 표 (643 MB) | **예** | 출력 투영으로 씀 (`Group::Embedding`). 판단으로 돌아가면 내려감 |
| 비전 타워 | **아니오** | 입력은 텍스트뿐 |

단계 이름은 `zoro:글쓰기` 입니다. 입력 토큰의 임베딩은 판단과 같이 파일에서 필요한 행만 읽습니다.

텍스트 블록은 두 방식 중 하나로 올라옵니다 (`ZoroModel` 의 `StreamMode`).

- **상주(기본, 예산에 들어갈 때)**: 첫 판단에서 32개를 한 번에 올리고, 다음 판단부터는 다시 읽지 않습니다. 다른 모델이 장치를 쓰러 올 때까지 남습니다.
- **스트리밍(예산이 빠듯할 때)**: 블록을 구간으로 나눠 구간마다 `enter` 합니다. 다음 구간을 올리기 전에 이전 구간이 먼저 내려가서, 최대 상주량은 가장 큰 구간 하나입니다. 판단마다 파일에서 다시 읽으므로 느립니다.

고르는 방법: 기본은 `Auto` 입니다. 장치 여유 메모리에서 1024 MB 를 뺀 값(`ZOROGRAVITY_VRAM_RESERVE_MB`)을 가중치 예산으로 잡고, 블록 전체가 들어가면 상주, 아니면 예산에 맞게 구간을 나눕니다.

| 환경 변수 | 뜻 |
| --- | --- |
| `ZOROGRAVITY_VRAM_BUDGET_MB` | 가중치 합계의 상한을 직접 지정 |
| `ZOROGRAVITY_VRAM_RESERVE_MB` | 활성값 · 작업 버퍼용으로 비워 둘 양 (기본 1024). 상한을 직접 지정하지 않을 때만 |
| `ZOROGRAVITY_ZORO_STREAM_BLOCKS` | `auto`(기본) · `resident`(= 0) · 숫자 N (블록 N 개씩 올렸다 내림) |
| `ZOROGRAVITY_ZORO_PROFILE` | `1` 이면 판단 1회의 층 종류별 시간을 표준 오류로 출력 (측정하느라 느려짐) |
| `ZOROGRAVITY_VRAM_HEADROOM_MB` · `ZOROGRAVITY_ALLOW_HOST_WEIGHTS` | 장치 메모리가 모자랄 때의 방어 (아래 절) |

### gocr 문서 인식 (비전 → 언어)

`ai::ocr::OcrEngine` 이 사용자가 말한 흐름을 구조로 고정합니다.

1. **비전 단계**: 비전 타워만 올립니다. 언어 가중치(임베딩 · 텍스트 블록 · 출력)는 장치에 없습니다. 이미지가 여러 장이면 **모두 한 번에** 인코딩합니다.
2. **전환**: 핸들을 놓고 비전을 내립니다. 비전 단계의 결과(특징)만 다음 단계로 넘어갑니다.
3. **언어 단계**: 언어 가중치만 올려 디코딩합니다. `LanguageWeights` 구조체에는 비전 가중치를 담는 칸이 없습니다.

장마다 비전과 언어를 오가며 올렸다 내리지 않는 것은 logis-center 가 "SigLIP2 를 컨텍스트마다 올렸다 내리면 OOM" 이라서 한 번 인코딩하고 즉시 반환하는 것과 같은 이유입니다.

계산은 `ai::gocr` 가 맡습니다 (`VisionEncoder` · `LanguageDecoder` 구현). 토큰 임베딩은 표를 올리지 않고 쓰는 행만 파일에서 읽습니다.

### siglip2 크롭 (비전 타워만)

페이지를 읽을 때는 비전 타워(`vision_model.*`)만 올립니다. 텍스트 타워(`text_model.*`)는 앵커 문구를 새로 인코딩할 때만 쓰고, 실행 중에는 올라오지 않습니다 (시각 앵커는 파일에 있습니다).
문서 한 장은 **SigLIP2 비전 → gocr 비전 → gocr 언어** 순서이고, 앞 단계를 내린 뒤에 다음 단계를 올립니다. 페이지가 여러 장이면 `DocumentReader::read_pages` 가 계획을 모두 세운 뒤 조각을 한꺼번에 읽어서 모델이 페이지마다 오가지 않습니다.

### 모델 사이의 전환

zoro 판단과 gocr 인식이 한 장치를 번갈아 쓸 때 같은 `SharedResidency`(= `Arc<Mutex<Residency>>`)를 공유합니다. 한 호출이 끝나기 전에는 다른 호출이 장치를 가져가지 못합니다. 호출이 끝난 뒤에 다른 모델이 오면 그때 내려갑니다. 가중치는 다음 모델이 올 때까지 남아 있어서, 같은 모델을 연달아 쓰면 다시 읽지 않습니다.

## 실측 (AMD Radeon RX 6600 8 GB, 실제 q8 GGUF)

`cargo run -p zorogravity-core --example residency_check` (Vulkan), ROCm 은 `target-rocm` 빌드로 같은 예제를 실행했습니다.

단계마다 장치 여유 메모리(MB). 처음 여유는 Vulkan 7146, ROCm 7991 입니다.

| 단계 | 올라온 것 | Vulkan 여유 | ROCm 여유 |
| --- | --- | --- | --- |
| 1 gocr 비전 | 비전만 | 7146 (일반 텐서라 아래 참고) | 7159 |
| 2 gocr 언어 | 임베딩 + 블록 16 + 출력 (비전은 내려감) | 6415 | 7255 |
| 3 zoro 텍스트 | 블록 32 + 출력 (gocr 는 모두 내려감) | 3300 | 4279 |
| 4 gocr 비전 (다시) | 비전만 (zoro 는 모두 내려감) | 7146 | 7159 |
| 5 모두 내림 | 없음 | 7146 (처음과 차이 0) | 7991 (차이 +32) |

- 모든 올림 · 내림 기록에서 **두 모델이 함께 올라온 적이 없습니다.** 예제와 시험이 기록을 되짚어 확인합니다.
- 내린 묶음의 메모리는 모두 돌아왔습니다. zoro 블록 3631 MB 를 내리면 여유가 3300 → 7146 MB 로 돌아옵니다.
- 올리고 내리는 시간은 아래 전환 비용 절에 있습니다.
- 스트리밍: 블록 8개씩 4구간으로 판단하면 최대 상주 **908 MB**, 판단 결과는 상주할 때와 같습니다 (확률 차이 1e-4 이하).

### 전환 비용

판단 → 문서 읽기 한 바퀴(zoro → SigLIP2 비전 → gocr 비전 → gocr 언어)를 `load_bench` 로 쟀습니다. 묶음을 내리고 올리는 시간만이고 계산은 뺐습니다.

| ROCm | 처음 | 일괄 해제 · 직접 업로드 · 예열 |
| --- | --- | --- |
| 프로세스 첫 바퀴 (파일이 OS 캐시에 있음) | 4.4 s | **1.9 s** |
| 이후 | 2.2 ~ 2.3 s | **1.9 s** |
| 파일이 OS 캐시에 없을 때 | 5.9 s | **2.1 s** |
| 내리기 합계 | 0.17 s | 0.15 s |

묶음별 (이후 바퀴, ROCm): zoro 3.8 GB 1.1 s, SigLIP2 비전 0.29 s, gocr 비전 0.28 s, gocr 언어 0.19 s.

- **비전 타워 직접 업로드**: 변환이 없는 텐서는 CPU 사본을 만들지 않고 매핑에서 바로 장치로 올립니다 (1.9 → 3.0 GB/s). 변환이 있는 텐서만 CPU 를 거칩니다 (`Prepare::touches`).
- **배경 예열**: 모델을 열 때 쓸 범위를 배경 스레드가 읽습니다 (`WeightFile::warm`). OS 미리 읽기를 요청한 뒤 페이지를 하나씩 건드려 프로세스에 매핑합니다. Windows 의 미리 읽기는 페이지를 메모리로 가져올 뿐이라 첫 사용의 소프트 폴트가 남기 때문입니다. 예열을 끄면 첫 바퀴가 3.3 s 입니다 (`ZOROGRAVITY_WARM=0`). 장치에는 아무것도 올리지 않으므로 한 번에 한 모델 규칙과 무관합니다.
- **일괄 해제**: 함께 내리는 묶음은 정리를 한 번만 합니다. 쓰는 곳이 남은 묶음이 하나라도 있으면 아무것도 내리지 않습니다. 시간 차이는 작습니다 (ROCm 0.17 → 0.15 s).
- Vulkan 은 거의 그대로입니다 (한 바퀴 3.5 ~ 3.7 s, 내리기 0.65 s). 일반 텐서가 호스트 메모리에 있어서 업로드가 복사 한 번이고, 내리는 시간은 정리 횟수가 아니라 버퍼 해제에 있습니다.

전환이 줄면서 문서 읽기도 빨라졌습니다. 합성 서식 64장을 8장씩 묶어 읽으면 장당 10.75 → **8.70 s** 이고, 값 그대로 읽힘은 378/440 으로 같습니다 (오독 목록까지 같음). 대부분은 언어 디코딩이 빨라진 값입니다 ([gpu-backends.md](gpu-backends.md) 3.6절).

### Vulkan 에서의 메모리 배치 (알아야 하는 점)

이 PC 처럼 독립 GPU 에 Vulkan 을 쓰면 **양자화(Q8_0) 가중치만 VRAM 에 올라갑니다.** 일반 텐서(활성값 · F32 정규화 가중치 · BF16 비전 타워)는 포크가 호스트에서 보이는 메모리(시스템 RAM)에 버퍼를 잡습니다 (`alloc_buffer`: "mapped host visible buffer"). 그래서

- `Device::mem_info()` 는 Q8_0 가중치가 쓴 장치 힙만 보여 줍니다. 비전 타워 1656 MB 를 올려도 여유가 변하지 않습니다.
- 이 경우는 `Residency::tensor_buffer_bytes()` (Vulkan 의 할당 바이트)로 봅니다. 비전을 올리면 0 → 1656 MB, 내리면 1656 → 0 MB 로 정확히 움직였습니다. 즉 비전을 내려서 돌려받는 것은 VRAM 이 아니라 **RAM** 입니다.
- ROCm 은 모든 텐서가 장치 메모리에 있습니다. 비전 타워는 BF16 그대로라 828 MB 이고, 내리면 장치 여유로 돌아옵니다.

가중치 예산(`Budget`)은 두 경우 모두 올린 바이트를 센 보수적인 값입니다.

## GPU 메모리가 모자랄 때 (조용히 수치가 달라지는 문제와 방어)

**겪은 일**: 같은 GPU 에서 zoro 프로세스를 동시에 여러 개 돌렸더니 같은 질문의 판단 확률이 실행마다 달랐습니다 (예: 0.9356 / 0.9242 / 0.9304). 같은 프로세스 안에서는 비트 단위로 같았고, 층별 체크섬을 비교하니 앞 25개 층은 모든 실행에서 같고 **마지막 층들(26 ~ 31)부터** 갈라졌습니다. 다른 GPU 프로세스를 모두 끄고 같은 실행을 8번 되풀이하니 8번 모두 같은 값(0.9282722)이 나왔습니다.

**원인**: 포크의 Vulkan 백엔드(`QVulkanStorage::from_bytes`)는 Q8_0 가중치를 GPU 에 올리다가 장치 메모리가 모자라면 오류를 내지 않고 **호스트 메모리에 그대로 둡니다.** 그 가중치를 쓰는 층은 CPU 경로(활성값도 8비트로 줄임)로 계산되어 수치가 달라집니다. 가중치는 앞 층부터 올라가므로 모자란 쪽은 마지막 층들이고, 다른 프로세스가 점유한 양에 따라 갈라지는 층이 바뀝니다.

**재현** (`pressure_probe` 예제, 방어를 끄고 VRAM 을 양자화 가중치로 채움, 전체가 올라가면 장치 여유가 약 3846 MB 줄어듦):

| 남긴 장치 여유 | 적재로 줄어든 장치 여유 | 판단 확률 (NORMAL) | 기준과의 최대 차이 |
| --- | --- | --- | --- |
| 충분 | 3846 MB (전부) | 0.9282722 | — |
| 3400 MB | 2889 MB | 0.9215 | 6.7e-3 |
| 3000 MB | 2530 MB | 0.9187 | 9.5e-3 |
| 2048 MB | 1594 MB | 0.9334 | 5.1e-3 |

**방어** (`Residency::load_one`, 기본으로 켜져 있음):

1. **올리기 전**: 장치 여유가 `묶음이 장치 힙에 차지할 크기 + 여유분(기본 640 MB, 포크 자신의 여유분 512 MB 보다 조금 크게)` 보다 작으면 `DeviceMemoryShort` 오류로 거부합니다. 이때는 아무것도 올리지 않습니다.
2. **올린 뒤**: 실제로 줄어든 장치 여유가 예상보다 10% (최소 64 MB) 넘게 모자라면 일부가 호스트에 남은 것이므로 올린 것을 되돌리고 `WeightsLeftOnHost` 오류를 냅니다.

| 환경 변수 | 뜻 |
| --- | --- |
| `ZOROGRAVITY_VRAM_HEADROOM_MB` | 올리기 전에 남아 있어야 할 여유분 (기본 640) |
| `ZOROGRAVITY_ALLOW_HOST_WEIGHTS=1` | 위 두 검사를 끕니다. 수치가 실행마다 달라질 수 있어 진단용입니다 |

검증: `memory_pressure_is_reported_instead_of_silently_changing_the_numbers` (`real_models`). 여유를 2 GB 로 줄이면 "블록 0..32 묶음은 장치 메모리 3825 MB 가 필요한데 여유가 2106 MB 뿐입니다" 로 거부되고, 메모리를 돌려주면 처음과 소수점 6자리까지 같은 확률로 복구됩니다.

**한계**: 여유 메모리는 다른 프로그램의 동시 사용으로 검사와 적재 사이에 바뀔 수 있습니다. 검사는 흔한 경우를 막는 것이고, 근본적으로는 포크가 호스트로 내려앉지 않고 오류를 내거나 `QTensor` 가 장치 상주 여부를 알려 주면 정확해집니다 (포크 수정은 하지 않았습니다). ROCm 은 할당 실패가 오류로 돌아옵니다.

**재현성 진단**: `ZOROGRAVITY_ZORO_TRACE=1` 이면 층마다 출력의 체크섬을 표준 오류로 냅니다. 두 실행의 출력을 비교하면 처음 달라지는 층을 찾을 수 있습니다.

## 검증

- `cargo test -p zorogravity-core --lib residency ocr zoro` — 합성 GGUF 로 규칙을 확인합니다 (필요한 묶음만 올림, 다음 단계에서 내림, 모델 전환 때 먼저 내림, 핸들을 쥐면 내리기 거부, 예산 초과는 형식 있는 오류, 스트리밍과 상주의 결과가 같음, 쓰지 않는 비전 · 임베딩 표는 올라온 적이 없음).
- `cargo test -p zorogravity-core --test real_models -- --ignored --nocapture --test-threads 1` — 실제 파일과 실제 장치로 같은 규칙과 zoro ↔ gocr 교대를 확인합니다.
- `residency_check` 예제 — 위 표를 만든 측정입니다.

## 한계

- 상주 관리자는 호출 단위로 장치를 독점합니다. 판단 하나가 끝나야 OCR 이 시작할 수 있습니다. 동시에 두 요청이 들어오면 순서대로 처리됩니다.
- 스트리밍은 판단마다 파일에서 다시 읽습니다. 예산에 들어가는 한 상주가 훨씬 빠릅니다 (판단 0.7 ~ 1.5 s 대 수 초).
- 장치 여유 메모리는 다른 프로그램의 사용에도 움직입니다. 기록은 진단용이고, 반환 여부를 판정하는 시험은 허용 오차를 둡니다.
