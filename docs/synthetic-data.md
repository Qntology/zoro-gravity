# 합성 데이터 전제

zorogravity 는 지금 **정부 API 와 데이터 파이프라인 없이** 진행합니다. 실제 시스템이라면 연계로 받아 올 관계망과 공공 대장을 **합성 데이터로 DB 에 미리 넣어 둔 상태**에서 심사합니다.

이 문서는 그 전제를 정의합니다. 무엇을 넣어 두는지, 어떻게 쓰는지, 실제 연계가 생기면 어디가 바뀌는지를 적습니다.

> 모든 값은 합성입니다. 실제 사람 · 기관 · 계좌 · 건축물이 아닙니다.
> 이 데이터로 잰 비율은 동작 확인용입니다. 운영 수치로 쓰면 안 됩니다.

## 1. 왜 필요한가

명세의 Gate 3 는 관계망(`tb_graph_entities`, 명세 Part 1 Table 3)에서 숨은 관계를 찾습니다. 이 관계망은 원래 민원이 쌓이면서 만들어지거나 외부 연계로 들어옵니다. 지금은 둘 다 없습니다.

| 빠진 것 | 없으면 생기는 일 | 합성 DB 가 대신하는 것 |
| --- | --- | --- |
| 가족 · 세대 · 계좌 관계 연계 | 위장 임차를 찾을 수 없음 | `edges` 의 혈연 · 세대 · 계좌 공유 |
| 법인 · 단체 임원 정보 | 특수관계 거래처를 찾을 수 없음 | `edges` 의 임원 · 배우자 · 대표 |
| 공공 대장 연계 | 서류 없는 민원인은 모두 창구로 가야 함 | `registries` 의 임대차 · 거래 · 카드 · 필증 |
| 건축물 위반 이력 | 위반건축물을 찾을 수 없음 | `buildings` 의 `violation` |

## 2. 파일과 코드

| 위치 | 내용 |
| --- | --- |
| `core/fixtures/synthetic_db.json` | 시드 DB. 빌드할 때 프로그램에 들어갑니다 |
| `core/fixtures/scenarios.json` | N:N 검증 시나리오와 기대 결과 |
| `core/src/lattice.rs` | 시드를 읽고 조회합니다 (`Lattice`) |
| `core/src/evidence.rs` | 사건의 사실을 서류와 대장에서 채웁니다 (`enrich`) |
| `core/src/extract.rs` | 읽은 글자에서 항목을 뽑고, 대장으로 오독을 바로잡습니다 (`correct`) |

`data/` 는 실제 민원용으로 `.gitignore` 에 들어 있어서, 합성 시드는 `core/fixtures` 에 둡니다.

시드는 시작할 때 메모리로 읽고 바꾸지 않습니다. 사건 사이에 관계를 누적하지 않습니다 ([automation-mode.md](automation-mode.md) 5절, 법무 검토 전).

## 3. 시드 구조

명세 Table 3 의 노드 종류를 따릅니다.

| 묶음 | 건수 | 내용 |
| --- | --- | --- |
| `persons` | 37 | 성명, 생년월일 앞 6자리, 주소. 명세의 `PERSON` |
| `orgs` | 4 | 보조금 단체 |
| `vendors` | 5 | 거래처. 명세의 `CORP_VENDOR` |
| `accounts` | 17 | 계좌. 명세의 `BANK_ACCOUNT` |
| `buildings` | 5 | 건축물. 명세의 `BUILDING_PARCEL`. 위반 이력 포함 |
| `edges` | 18 | 관계 |

### 관계 종류

| `kind` | 뜻 | 임차 배제 규칙에서 가까운 연결인가 |
| --- | --- | --- |
| `family` | 혈연. `degree` 는 촌수 | 2촌 이내만 |
| `household` | 동일 세대. `year` 는 연도 | 예 |
| `shared_account` | 같은 계좌 사용 | 예 |
| `spouse` | 배우자 | 예 |
| `officer_of` | 단체의 임원 | 아니오. 특수관계 거래처 경로에서만 씁니다 |
| `represented_by` | 거래처의 대표 | 아니오. 특수관계 거래처 경로에서만 씁니다 |

### 공공 대장 (`registries`)

| 대장 | 대신하는 서류 | 실제라면 |
| --- | --- | --- |
| `leases` | 임대차계약서 | 공공 데이터 연계 자리 |
| `transfers` | 이체내역서 | 금융정보 조회 동의 후 연계 자리 |
| `subsidy_programs` | 통장사본 · 사업 정보 | 보조금 관리 시스템 자리 |
| `card_ledger` | 영수증철 | 보조금 전용 카드 내역 자리 |
| `tax_invoices` | 세금계산서 | 전자세금계산서 자리 |
| `hygiene_certs` | 위생교육필증 | 교육 기관 자료 자리 |
| `fire_certs` | 소방안전필증 | 소방 자료 자리 |
| `seal_registry` | 인감 등록 여부 | 인감 대장 자리 |

어떤 기관의 어떤 시스템과 실제로 연계할 수 있는지는 확인하지 않았습니다. 표의 "실제라면"은 자리를 설명할 뿐이고, 법적 근거와 연계 가능 여부는 별도 검토가 필요합니다.

**위임장은 대장으로 갈음하지 않습니다.** 위임자의 의사 표시 원본이기 때문입니다. 위임장과 신분증은 스캔하거나 창구에서 봅니다.

### 합성 규칙

시드와 함께 쓰는 값입니다. 실제 법령 값이 아니라 시험용입니다.

| 값 | 내용 |
| --- | --- |
| 위생교육필증 유효기간 | 발급일로부터 24개월 |
| 소방안전필증 유효기간 | 발급일로부터 12개월 |
| 입찰 회피 기준 | 같은 날 같은 거래처 합계 50만 원 이상을 50만 원 미만으로 나눠 결제 (명세 CAT_02) |
| 비인정 품목 | 유흥주점 거래처, 품목에 `주류` · `유흥` · `노래방` 포함 |
| 건축물 용도 | `근린생활시설` 이 들어가야 일반음식점 가능 |

## 4. 조회 방식

키오스크는 주민등록번호를 받지 않습니다. 그래서 명세 Part 4 §1.1 의 1차 후보군 방식으로 찾습니다.

```
성명 + 생년월일 앞 6자리 → persons 조회
  0명  → 창구 확인 ("관계망 미등록")
  1명  → 그 사람의 노드로 관계망 조회
  2명+ → 창구 확인 ("관계망 동명이인") — 추측하지 않습니다
```

찾은 노드의 식별자는 솔트 해시로만 사건에 붙습니다 (`Engine::node_hash`). 관계망 안의 다른 사람 이름은 동명이인을 가려낼 때만 쓰고, 공무원 화면에는 불리한 후보일 때 마스킹해서 보입니다.

스캔 값의 오독은 대장으로 바로잡습니다 (`extract.rs` 의 `correct`). 대장에 비슷한 값이 **하나뿐일 때만** 고칩니다.

| 값 | 비교 |
| --- | --- |
| 사람 | 성명과 생년월일을 합쳐 한 글자 차이 |
| 단체 · 거래처 · 주소 | 4~9자는 한 글자, 10자 이상은 두 글자 차이. 3자 이하는 고치지 않습니다 |
| 사업명 | 단체가 정해진 뒤 세 글자에 한 글자까지 |
| 영수증 | 승인번호가 카드 원장에 있으면 거래처 · 일시 · 품목을 원장 값으로 씁니다. 금액은 대조하려고 서류 값을 둡니다 |

**명세와 다른 점**: 명세의 2차 정밀 식별은 주민번호 해시와 주소 교집합입니다. 지금은 주민번호를 받지 않으므로 성명 + 생년월일이 하나로 정해질 때만 씁니다. 둘 이상이면 공무원이 신분증으로 구분합니다.

## 5. 증빙의 우선순위

사실 하나의 출처는 다음 순서입니다 ([evidence.rs](../core/src/evidence.rs)).

```
서류 스캔 > 합성 대장 > 없음 (창구 확인)
```

| 경우 | 동작 |
| --- | --- |
| 서류와 대장이 같음 | 서류 값 사용 |
| 서류와 대장이 다름 | 서류 값을 쓰되 창구 확인으로 보냄 (자동 확정 안 함) |
| 서류만 있음 | 서류 값 사용. 건축물은 대장이 없으면 창구 확인으로 보냄 (위반 표기는 못 읽으면 조용히 빠지기 때문) |
| 대장만 있음 | 대장 값 사용. 서류는 "대장"으로 확인된 것으로 기록 |
| 둘 다 없음 | 값을 지어내지 않음. 창구에서 공무원이 원본을 보고 넣음 |
| 스캔 신뢰도가 낮거나 못 읽음 | 해당 값을 창구 확인으로 보냄. 대장이 있으면 서류가 없는 경우와 같으므로 넘기지 않음 |
| 민원인이 스캔 값을 고침 | 심사에 쓰는 값이면 창구 확인으로 보냄. 상호 · 면적 · 연락처 · 용도처럼 심사에 쓰지 않는 값은 넘기지 않음 |
| 서류의 이름이 신청인과 다름 | 창구 확인으로 보냄 (임차인 · 예금주 · 위생교육필증 성명 · 위임장의 대리인과 위임자). 한 글자 차이는 오독으로 봄 |
| 서류의 주소가 신고 주소와 다름 | 창구 확인으로 보냄 (건축물대장 · 소방안전필증). 두 글자 차이까지는 오독으로 봄 |
| 스캔 영수증이 카드 원장과 다름 | 창구 확인으로 보냄 (금액 차이, 원장에 없는 승인번호) |
| 진술 서식의 값이 믿기 어려움 | 신청서 · 정산총괄표 · 영업신고서는 민원인 본인의 진술이므로 사람에게 넘기지 않고 키오스크에서 민원인이 확인 |

**대장 값은 민원인 화면에 보이지 않습니다.** 성명과 생년월일만으로 남의 계약 금액을 볼 수 있으면 안 되기 때문입니다. 차액을 묻는 소명 화면도 신분증 스캔으로 본인 확인이 된 뒤에만 나옵니다.

## 6. 민원별 필수 서류를 무엇으로 갈음하는가

| 민원 | 서류 | 서류 없을 때 |
| --- | --- | --- |
| 복지 | 신청서 · 금융정보동의서 | 키오스크 입력과 서명 |
| 복지 | 임대차계약서 · 이체내역서 | 대장 |
| 지원금 정산 | 정산총괄표 | 키오스크 입력 |
| 지원금 정산 | 영수증철 · 세금계산서 · 통장사본 | 대장 |
| 허가 · 신고 | 영업신고서 | 키오스크 입력 |
| 허가 · 신고 | 위생교육필증 · 소방안전필증 · 건축물대장 | 대장. 만료된 필증은 누락으로 봄 |
| 증명 · 대리 | 위임장 · 위임자 신분증 · 대리인 신분증 | **갈음 불가**. 스캔하거나 창구에서 확인 |
| 고충민원 | 없음 | 해당 없음 |

## 7. 자동 확정 조건에 끼치는 영향

자동 확정은 [automation-mode.md](automation-mode.md) 3절의 조건을 모두 만족해야 합니다. 키오스크 접수 건에는 다음이 더 붙습니다.

- 필수 서류가 스캔 · 대장 · 키오스크 서명으로 모두 확인됨
- 창구에서 확인할 일(`pending`)이 없음
- **신분증 스캔으로 본인 확인이 됨.** 신분증이 없으면 공무원이 확인합니다

## 8. 실제 연계가 생기면 바뀌는 곳

| 바뀌는 곳 | 내용 |
| --- | --- |
| `Lattice` 의 조회 함수 | 시드 대신 실제 연계를 부릅니다. 함수 모양은 유지합니다 |
| `core/fixtures/synthetic_db.json` | 시험 전용으로 남깁니다 |
| 식별 방식 | 성명 + 생년월일 대신 인증된 식별자를 씁니다 (4절) |
| 합성 규칙 | 법령 값으로 바꿉니다 (3절) |

바뀌지 않는 곳은 `evidence.rs` 의 우선순위, 규칙 게이트, 자동화 정책, 공무원 화면입니다.

## 9. 시나리오

`core/fixtures/scenarios.json` 의 31개 시나리오를 서류 상태 4단계로 돌립니다 (복지 11, 지원금 5, 허가 6, 증명 3, 고충 6).

| 서류 상태 | 뜻 |
| --- | --- |
| `none` | 서류도 신분증도 없음 |
| `id_only` | 신분증만 있음 |
| `partial` | 신분증 + 서류 절반 |
| `full` | 신분증 + 서류 전부 |

서류 이미지는 `scripts/gen_case_docs.py` 가 시나리오 값으로 만듭니다. 서명란 판별 시험용으로 서명한 쪽과 안 한 쪽을 같은 수로 만든 `sign-*` 묶음도 함께 생깁니다.

시나리오별 기대 결과는 파일에 있고, 검증 결과는 [stabilization-report.md](stabilization-report.md) 에 있습니다.
