# 안정화 결과

민원인 서류가 있는 경우와 없는 경우를 민원 종류별로 N:N 으로 돌려, 처음부터 끝까지 다시 검증하고 고친 기록입니다. 기준은 **자동화 절차**와 **공무원 개입** 두 가지입니다.

> 모든 수치는 합성 데이터로 잰 값입니다. 정부 API 와 데이터 파이프라인이 없어서 관계망과 대장을 DB 에 미리 넣어 두었습니다 ([synthetic-data.md](synthetic-data.md)). 실제 민원의 비율로 쓰면 안 됩니다.

시연 영상은 `out/video/zorogravity-demo.mp4` 입니다 (5분 59초, 1080p, 저장소에는 넣지 않습니다). 민원인과 공무원 창을 같은 시각으로 녹화해 교차 편집했고, 모델이 쓰이는 순간에는 그 모델이 무엇을 했는지 장면을 끼워 넣었습니다 (3.4). 1부는 자동화 절차 4건, 2부는 공무원 개입 5건입니다. 긴 대기는 빨리 감았고, 오른쪽 열에 실제 경과 시간, 지금 쓰는 모델, GPU 에 올라온 가중치를 적었습니다. 화면의 숫자와 글은 모두 그 실행의 모델 기록에서 왔습니다.

## 1. 결론

두 기준 모두 통과했습니다.

| 기준 | 결과 |
| --- | --- |
| 자동화: 사고 | **0건.** 모든 층에서 자동 확정하면 안 되는 건이 자동 확정되지 않았습니다 |
| 자동화: 처리 | 자동 확정 대상 24건 중 서류 정답 값 **24건**, 실제 OCR **24건**, 처음 보는 서류 **24건** |
| 자동화: 불리한 처분 | 자동 확정 0건 |
| 공무원: 막다른 길 | **0건.** 공무원에게 간 124건을 모두 끝까지 처리했습니다 |
| 공무원: 규칙 차단 | 함정 행위 40회 **모두 차단** |
| 공무원: 정보 누출 | 키오스크 화면 **0건** |
| 재현성 | 같은 입력을 두 번 돌려 판정 · 확신도 · 부서 차이 **0건** |
| 앱 E2E | 민원인 · 공무원 12개 흐름 **최종 빌드 연속 2회 통과** (실제 모델 · 실제 앱) |
| 절차 | 키오스크 4단계 → 3단계. 복지 입력 12개 → 서류가 있으면 0~1칸. 공무원 복지 건 8동작 → 2~4동작 |

## 2. 안정화 기준

시작하기 전에 정한 기준입니다.

### 2.1 자동화 절차

| 번호 | 기준 |
| --- | --- |
| A1 | 자동 확정을 기대하지 않은 건이 자동 확정되지 않는다 (사고 0) |
| A2 | 불리한 처분은 어떤 층에서도 자동으로 끝나지 않는다 |
| A3 | 자동 확정 대상의 처리 건수를 잰다. 놓침은 사고가 아니라 공무원 일거리로 센다 |
| A4 | 처분 기준 0.95 를 낮추지 않는다. 함정 사례 통과 0 을 유지한다 |
| A5 | 자동 확정마다 감사 기록이 남고 사후 감사 대상을 고른다 |
| A6 | 같은 입력을 다시 돌려도 결과가 같다 |

### 2.2 공무원 개입

| 번호 | 기준 |
| --- | --- |
| O1 | 자동으로 끝나지 않는 건은 모두 사유와 함께 공무원에게 간다 |
| O2 | 공무원에게 간 건은 어떤 서류 상태에서도 끝낼 수 있다 (막다른 길 0) |
| O3 | 입증 없는 승인, 무증빙 금액 수정, 강제 진입은 막히고 기록된다 |
| O4 | 키오스크에 내부 정보가 보이지 않는다 |
| O5 | 실제 앱에서 두 화면이 이어서 동작한다. 연속으로 통과한다 |
| O6 | 실제 업무에 필요한 확인은 지키면서 단계와 입력을 줄인다 |

## 3. 층별 결과

| 층 | 무엇을 쓰는가 | 조합 | 자동 확정 (대상 24) | 사고 | 후보 불일치 |
| --- | --- | --- | --- | --- | --- |
| L1 규칙 | 서류 정답 값 + 모델 대역 | 124 × 운영 모드 2 = 248 | 24 | 0 | 0 |
| L2 실제 모델 | 서류 정답 값 + Zoro-1 | 124 | 24 | 0 | 0 |
| L3 OCR | 합성 서류 이미지 + gocr + SigLIP2 + 추출 + Zoro-1 | 124 | 24 | 0 | 0 |
| L3 시드 23 | 서류 154장. 첫 평가 22건을 보고 추출을 고친 뒤의 값 | 124 | 24 | 0 | 0 |
| L3 시드 37 | **처음 보는 서류 154장.** 코드를 고정한 뒤 평가만 함 | 124 | 24 | 0 | 0 |
| L4 앱 | 실제 앱 · 실제 모델 · 두 창 | 12개 흐름 | 해당 4/4 | 0 | - |

L3 는 처음에 시드 11 이 23건, 시드 23 이 22건이었습니다. 놓친 건은 모두 신분증 이름이나 주소를 못 읽은 경우로, 공무원에게 가서 안전한 쪽으로 멈춘 것입니다. 신분증 이름 후보를 둘 다 대장과 맞추고, 못 읽은 값을 대장이 확인하면 넘기지 않도록 고친 뒤 두 시드 모두 24건이 되었습니다 (4절). 시드 23 의 결과를 보고 고쳤으므로 **과적합을 재는 값은 시드 37 입니다.**

L2 와 L3 를 같은 입력으로 두 번 돌렸을 때 판정 · 확신도 · 부서가 모두 같았습니다 (차이 0건). 공무원에게 간 건에는 모두 사유가 있고, 자동 확정된 건은 모두 유리한 처분입니다. 앱에서 자동 확정된 건은 감사 기록에 남습니다. 사후 감사 표시는 `governance.rs` 시험이 확인합니다.

고충민원 부서 분류는 시나리오 6종 × 서류 상태 4단계에서 24/24 맞았습니다.

### 3.1 민원 × 서류 상태 (자동 확정 건수 / 전체)

L3 시드 11 기준입니다. 시드 23 도 같은 표입니다. `대상` 은 자동 확정을 기대한 건수입니다.

| 민원 | 서류 없음 | 신분증만 | 서류 절반 | 서류 전부 |
| --- | --- | --- | --- | --- |
| 복지 (11종) | 0 / 11 | 5 / 11 (대상 5) | 5 / 11 (대상 5) | 4 / 11 (대상 4) |
| 지원금 정산 (5종) | 0 / 5 | 2 / 5 (대상 2) | 1 / 5 (대상 1) | 1 / 5 (대상 1) |
| 허가 · 신고 (6종) | 0 / 6 | 2 / 6 (대상 2) | 2 / 6 (대상 2) | 1 / 6 (대상 1) |
| 증명 · 대리 (3종) | 0 / 3 | 0 / 3 | 0 / 3 | 1 / 3 (대상 1) |
| 고충민원 (6종) | 0 / 6 | 0 / 6 | 0 / 6 | 0 / 6 |

- **서류 없음은 모두 공무원에게 갑니다.** 신분증이 없으면 본인 확인이 안 되기 때문입니다. 대장으로 서류는 확인되므로 공무원이 할 일은 본인 확인 하나입니다.
- **신분증만 있으면 대장으로 끝납니다.** 다만 증명 · 대리는 위임장이 대장으로 갈음되지 않아 공무원에게 갑니다.
- 고충민원은 언제나 공무원이 부서를 정해 이첩합니다.
- 함정 시나리오가 많은 구성이라 자동 확정 건수는 **비율로 읽으면 안 됩니다.**

다른 민원의 서류를 낸 경우 12조합은 모두 자동 확정 없이 "필요 없는 서류" 사유로 공무원에게 갔습니다.

### 3.2 문서 읽기

합성 서류 154장씩 세 묶음입니다. 시드 11 은 추출 규칙을 만들 때 본 서류, 시드 23 은 첫 평가 뒤 두 가지를 고칠 때 본 서류, 시드 37 은 코드를 고정한 뒤 처음 읽은 서류입니다.

| 항목 | 시드 11 | 시드 23 | 시드 37 (처음 봄) |
| --- | --- | --- | --- |
| 서류 종류 | 154 / 154 | 154 / 154 | 154 / 154 |
| 민원 종류 추정 | 31 / 31 | 31 / 31 | 31 / 31 |
| 서명 · 날인 판별 | 66 / 66 | 66 / 66 | 66 / 66 |
| 항목 값 | 322 / 327 (98.5%) | 317 / 327 (96.9%) | 320 / 327 (97.9%) |

서명 판별에는 서명한 쪽과 안 한 쪽을 같은 수로 만든 시험이 들어 있고 오탐과 놓침이 모두 0입니다. 장당 읽기 시간은 약 9.6초입니다 (RX 6600, ROCm).

시드 11 · 23 의 틀린 값은 심사를 잘못 이끌지 않았습니다.

| 틀린 값 | 시드 11 | 시드 23 | 어떻게 걸러지는가 |
| --- | --- | --- | --- |
| 대장에 없는 사람의 신분증 이름 | 2 | 2 | 고충민원 신청인입니다. 민원인이 화면에서 고칩니다 |
| 이름 한 글자 오독 | 1 | 4 | 신청인과 한 글자 차이는 같은 사람으로 보고, 대장의 계약 · 계좌와 맞춥니다 |
| 칸을 못 읽음 | 1 | 4 | 민원인이 직접 적거나 대장이 확인합니다 |
| 상호 | 1 | 0 | 심사에 쓰지 않는 값입니다 |

시드 37 의 틀린 7건도 같은 종류입니다. 고충민원 신청인의 이름 2건, 이름 한 글자 오독 3건, 상호 1건, 진정서 본문의 오독 1건이고 심사 결과를 바꾸지 않았습니다.

글자 신뢰도만으로는 다 잡지 못합니다. 기준 0.9 에서 서류에 표시되는 오독은 시드 11 이 5건 중 3건, 시드 23 이 10건 중 7건입니다. 기준을 0.5 에서 0.9 로 올려도 대장이 확인한 값은 넘기지 않으므로 자동 확정은 줄지 않았습니다.

### 3.3 앱 E2E

두 창을 CDP 로 붙여 실제 앱을 끝까지 돌렸습니다. 서류는 스캐너 폴더에 넣었습니다. 시간은 최종 빌드에서 사람 대기 없이 잰 값입니다.

| 흐름 | 시나리오 | 서류 | 결과 | 시간 | 민원인 입력 / 서류에서 읽음 | 공무원 동작 |
| --- | --- | --- | --- | --- | --- | --- |
| A1 | 복지 정상 | 5장 | 자동 확정 | 51초 | 1 / 3 | 0 |
| A2 | 정산 정상 | 5장 | 자동 확정 | 45초 | 0 / 5 | 0 |
| A3 | 영업신고 정상 | 신분증 | 자동 확정 | 14초 | 4 / 2 | 0 |
| A4 | 대리 발급 정상 | 3장 | 자동 확정 | 26초 | 1 / 7 | 0 |
| O1 | 복지 위장 임차 | 5장 | 공무원 반려 | 64초 | 0 / 4 | 2 + 열람 · 승인 시도 3 |
| O2 | 복지 서류 없음 | 없음 | 공무원 확정 | 11초 | 4 / 0 | 3 |
| O3 | 정산 증빙 부족 | 5장 | 감액 정산 | 48초 | 0 / 5 | 2 |
| O4 | 위반건축물 | 신분증 | 공무원 반려 | 15초 | 4 / 2 | 2 + 승인 시도 2 |
| O5 | 서명 없는 위임장 | 3장 | 보완요구 | 26초 | 1 / 7 | 2 |
| O6 | 손글씨 진정서 | 2장 | 부서 이첩 | 18초 | 0 / 3 | 3 |
| O7 | 대장에 없는 계약 | 5장 | 공무원 확정 | 62초 | 0 / 4 | 3 |
| O8 | 약한 서명 재요청 | 없음 | 공무원 확정 | 11초 | 4 / 0 | 3 |

공무원 동작은 건을 여는 것을 포함한 수입니다. O6 에서는 민원인이 본문 오독을 고쳤습니다. 모든 흐름에서 키오스크 화면에 내부 정보가 없는 것을 확인했습니다.

최종 빌드에서 연속 2회 12/12 입니다 (모델 기록을 켠 녹화 1회, 끈 실행 1회). 그 앞 빌드들에서도 연속 7회 12/12 였습니다. 더 앞의 실행에서 나온 실패는 시험 스크립트의 문제였습니다 (7절).

### 3.4 모델이 쓰이는 방식 (실측)

앱을 `ZOROGRAVITY_TRACE` 로 띄우면 모델이 언제 무엇을 했는지 파일에 남습니다 (`core/src/ai/trace.rs`). 아래는 녹화한 12개 흐름의 기록입니다. 기본 기록에는 민원 내용이 없습니다. 판단의 사실은 식별 정보를 뺀 값이고, 문서와 글쓰기는 좌표 · 개수 · 시간만 남깁니다. 영상의 읽은 글자와 모델이 쓴 글은 합성 서류 시연용으로 `ZOROGRAVITY_TRACE_TEXT=1` 을 켜서 얻었습니다. 실제 민원에서는 켜면 안 됩니다.

| 모델 | 언제 | 무엇을 하나 | 실측 | GPU |
| --- | --- | --- | --- | --- |
| SigLIP2 | 스캔 첫 단계 | 페이지를 패치 특징으로 바꿔 제목 · 입력란 · 표 · 서명 조각을 고릅니다. 안내문은 버립니다 | 장당 0.24초 | 0.86 GB |
| gocr 비전 | 스캔 둘째 단계 | 고른 조각을 글자 특징으로 바꿉니다 | 조각당 0.36초 | 0.87 GB |
| gocr 언어 | 스캔 셋째 단계 | 특징을 보고 글자를 씁니다. 표는 칸 구조를 지킵니다 | 조각당 0.49초, 토큰당 11 ms | 0.62 GB |
| Zoro-1 판단 | 접수, 창구 확인 뒤 재심사 | 식별 정보 없는 사실을 읽고 선택지 확률을 냅니다. 글을 쓰지 않습니다 | 중앙값 0.63초 (47번) | 3.81 GB |
| Zoro-1 글쓰기 | 판정 뒤 | 심사 의견 · 고충 요약 초안을 씁니다. 처분을 바꾸지 않습니다 | 중앙값 3.8초, 토큰당 129 ms (12번) | 4.48 GB |

- **시간은 대부분 gocr 입니다.** 서류 5장 건에서 모델 시간 약 52초 가운데 gocr 가 43초입니다. 조각 47개를 읽습니다.
- **GPU 에는 한 번에 한 모델만 있습니다.** 가장 많이 쓸 때 4.48 GB 입니다 (RX 6600 8 GB). 12개 흐름에서 가중치를 141번 올리고 내렸고 합계 25초입니다.
- **서류가 없으면 문서 모델은 올라오지 않습니다** (O2, O8).
- **모델은 규칙의 후보를 바꾸지 못합니다.** 증빙 부족 건(O3)에서 모델은 요건 충족 쪽(0.612)이었지만 규칙 후보가 유지되어 공무원에게 갔습니다.

**Gate 0 의 민원 종류 질문은 없앴습니다.** 처음에는 모델이 서류 이름만 보고 민원 종류를 골랐는데, 복지 서류만 맞혔습니다 (복지 0.40). 지원금 서류는 복지 0.44, 증명 서류는 복지 0.31, 진정서는 지원금 0.78 로 틀렸습니다. 분류는 접수 양식이 정하고 이 답은 파이프라인 어디에서도 읽지 않았으므로 쓸모없는 질문이었습니다. 질문을 뺀 뒤 L1 ~ L4 결과는 같았고, 12개 흐름의 판단 호출이 58번에서 47번으로 줄었습니다. 제출 한 번에 약 0.6초가 줄었고, N:N 124개 조합의 평가 시간은 389초에서 341초가 되었습니다.

## 4. 모델 로직의 정밀도 개선

| 개선 | 내용 | 결과 |
| --- | --- | --- |
| 글자별 신뢰도 | 조각 하나의 최솟값은 다른 칸 때문에 낮아집니다. 토큰 신뢰도를 글자로 옮겨 값 단위로 봅니다 (`char_confidence`) | 기준 0.9 에서 오독의 60~70% 표시, 자동 확정 감소 없음 |
| 항목 추출 | 서식별 항목 이름과 머리 칸 위치로 값을 뽑습니다 (`extract.rs`) | 첫 측정 86.6% (90장) → 98.5%, 처음 보는 서류 97.9% |
| 머리 칸 처리 | 세로로 합친 칸은 묶음의 가운데 줄에서 읽힙니다. 줄 순서가 아니라 위치가 가까운 머리 칸을 씁니다 | 임대인 · 임차인 뒤바뀜 해소 |
| 대장 보정 | 대장에 비슷한 값이 하나뿐일 때만 고칩니다 | 반복 오독(`협의회` → `험의회`)이 사라졌습니다 |
| 신분증 이름 | 조각이 겹쳐 두 번 읽은 후보를 둘 다 대장과 맞춥니다. 제목이 겹쳐 읽힌 줄은 후보에서 뺍니다 | 대장에 있는 사람의 이름 오독 해소 |
| 대장이 확인한 값 | 못 읽었거나 신뢰도가 낮아도 대장이 확인해 주면 사람에게 넘기지 않습니다. 서류가 없는 경우와 같기 때문입니다 | 자동 확정 시드 11 은 23 → 24, 시드 23 은 22 → 24 |
| 승인번호 대조 | 영수증은 카드 원장의 승인번호로 맞춥니다. 금액이 다르거나 원장에 없으면 공무원에게 갑니다 | 영수증 항목 78/78 |
| 교차 대조 | 서류의 이름 · 주소가 신청과 맞는지 봅니다 | 남의 서류 시나리오 2종 추가, 자동 확정 차단 |
| 진술과 증빙 구분 | 신청서처럼 본인 진술인 서식의 불확실한 값은 민원인이 확인합니다. 증빙 서류의 필수 값만 공무원에게 갑니다 | 불필요한 공무원 확인 감소 |
| 서명 없는 위임장 | 서류로 치지 않습니다 | 보완요구가 가능해졌습니다 (7절) |
| 동명이인 사실 문구 | 사람을 가른 근거를 그대로 적습니다: `예 (생년월일이 달라 다른 사람으로 확인)` | 0.944 → 0.952, 놓침 3건 해소 |

### 동명이인 문구에 대해

처분 기준 0.95 는 낮추지 않고 모델에 주는 사실을 고쳤습니다. 다만 근거가 약합니다.

- **먼저 시도한 방법은 실패했습니다.** 기준별 사실(친족 · 세대 · 계좌 아니오)을 모든 건에 넣었더니 깨끗한 건까지 모델이 다른 답을 내서 자동 확정이 사라졌습니다. 되돌렸습니다.
- 문구 다섯 개를 비교했고, 0.959 가 나온 `아니오 (이름만 같은 다른 사람)` 는 사실이 아니라서 버렸습니다.
- 고른 문구는 0.952 로 기준을 **겨우** 넘습니다. 고른 사례와 평가한 사례가 같고 시나리오도 하나입니다. 그림자 운영 없이는 믿을 만한 값이 아닙니다.

함정 사례 평가(`automation_eval`, 42건)는 지금 방식(기준별 최솟값, 0.95)에서 깨끗한 건 자동 18/23, 함정 통과 0/19 로 그대로입니다.

## 6. 절차 단순화

### 6.1 민원인

이전은 양식 입력 단계의 화면입니다 ([kiosk-form-plan.md](kiosk-form-plan.md) 10절).

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 단계 | 민원 선택 → 정보 입력 → 내용 확인 → 접수 완료 | 서류 넣기 → 내용 확인 → 결과 |
| 민원 선택 | 항상 | 서류가 있으면 생략 |
| 확인 화면 | 입력 뒤 별도 화면 | 입력 화면에 합침 |
| 결과 | 접수 번호만 | 그 자리에서 교부 문서 |

입력 항목 수입니다. 서명과 동의를 포함합니다.

| 민원 | 이전 | 서류 없음 | 서류 전부 + 신분증 (실측) |
| --- | --- | --- | --- |
| 복지 | 12 | 6 | 1 (읽지 못한 칸) |
| 지원금 정산 | 8 이상 (항목당 3 추가) | 5 | 0 |
| 허가 · 신고 | 10 | 6 | 신분증만일 때 4 |
| 증명 · 대리 | 9 | 9 | 2 (용도, 서명) |
| 고충민원 | 4 | 4 | 0 |

줄인 근거는 하나입니다. **민원인이 정할 값만 받습니다.** 계약 월세 · 이체액 · 필증 번호는 민원인이 정하는 값이 아니라 서류나 대장에서 오는 값입니다.

지키는 것도 있습니다.

- 금융정보 조회 동의와 서명은 종이 서명이 없으면 그대로 받습니다.
- 신분증이 없으면 공무원이 본인을 확인합니다.
- 위임장과 신분증 원본은 대장으로 갈음하지 않습니다.
- 차액 소명은 본인 확인이 끝난 뒤에만 묻습니다. 차액을 알려 주는 것 자체가 대장 값을 보이는 일이기 때문입니다.

### 6.2 공무원

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 사번 | 건마다 입력 | 콘솔 머리에서 한 번 |
| 체크리스트 | 필수 서류 전부 + 신분증 | 확인이 끝나지 않은 일만 |
| 사유 | 화면 아래 | 맨 위 |
| 처리 | 확정 하나 | 후보에 맞는 처리만 (확정 · 반려 · 보완요구 · 감액 · 고위험 승인) |
| 값 입력 | 없음 | 서류도 대장도 없을 때만 |

건을 여는 것부터 처리까지의 동작 수입니다. 이전 값은 화면 구성에서 센 값이고, 이후 값은 3.3 의 실측입니다.

| 민원 | 이전 | 이후 (실측) |
| --- | --- | --- |
| 복지 | 8 (열기, 사번, 체크 5, 확정) | 2~4 |
| 지원금 정산 | 9 (합계 입력 포함) | 2 |
| 허가 · 신고 | 8 | 2 |
| 증명 · 대리 | 7 | 2 |
| 고충민원 | 8 (체크 4, 부서, 사번, 이첩, 열기) | 3 |

## 7. 찾아서 고친 문제

| 문제 | 어떻게 찾았나 | 처리 |
| --- | --- | --- |
| gocr 이 열리지 않음. 받은 GGUF 의 메타데이터 키가 옛 이름(`zeze.*`) | 처음으로 실제 앱 경로를 돌림 | 읽을 때 새 이름으로 바꿈 (`alias_old_names`) |
| 서류가 없어 후보가 없는 건을 공무원이 끝낼 수 없음 | 공무원 N:N | 키오스크 건은 Gate 3 를 항상 돌리고, 창구 값을 넣으면 다시 심사 |
| 서명 없는 위임장에 보완요구를 할 수 없음 ("누락 서류 없음") | 공무원 동선 점검 | 서명 없는 위임장은 서류로 치지 않음 |
| 감액 정산이 두 번 눌러야 끝남 | 동선 점검 | 금액을 정한 결정은 후보 변경을 다시 묻지 않음 |
| 공무원 상세가 이전 건을 잠깐 보임 | 이전 E2E 의 간헐 실패 | 고를 때 비우고, 늦게 온 응답을 버림 |
| 대장에 없는 건축물의 위반 표기를 못 읽으면 조용히 빠질 수 있음 | 코드 검토 | 대장에 없는 건축물은 항상 공무원이 봄 |
| 입력 중 자리를 뜨면 앞 사람의 값이 화면에 남음 | 코드 검토 | 2분 동안 동작이 없으면 처음 화면으로 |
| 화면이 읽은 서류 값을 들고 있어서 바꿔 보낼 수 있음 | 코드 검토 | 읽은 값은 백엔드에 두고 접수 때 붙임 |
| 모델 추론 중 공무원 화면이 멈출 수 있음 | 코드 검토 | 엔진을 기다리는 명령을 메인 스레드 밖에서 실행 |

시험 스크립트 쪽 문제도 있었습니다. 소명 화면에서 답이 오기 전에 다음 단계로 넘어간 것과, 오독을 고친 건에서 공무원 본인 확인 체크를 하지 않은 것입니다. 둘 다 앱은 정상이었고 스크립트를 고쳤습니다.

## 8. 한계

1. **합성 데이터입니다.** 서류 이미지는 스크립트가 만들었고 관계망은 직접 넣었습니다. 실제 스캔 품질, 실제 손글씨, 실제 민원 분포로 검증한 것이 아닙니다.
2. **스캐너는 폴더로 대신합니다.** 실제 드라이버와 터치 장비는 시험하지 않았습니다.
3. **정부 연계가 없습니다.** 대장 조회 자리는 시드 조회입니다. 어떤 연계가 법적으로 가능한지는 검토 전입니다.
4. **자동화 모드의 법령 근거는 합성 문구입니다.** 켜기 전에 [automation-mode.md](automation-mode.md) 6~7절의 검토가 필요합니다.
5. **동명이인 확신도는 기준을 겨우 넘습니다** (4절).
6. **대장에 없는 사람의 신분증 이름은 고칠 수 없습니다.** 민원인이 고쳐야 하고, 고치면 공무원에게 갑니다.
7. **저장은 메모리뿐입니다.** 앱을 끄면 접수와 감사 기록이 사라집니다.
8. **공무원 사번은 입력만 받고 인증하지 않습니다.**
9. **설치본은 만들지 않았습니다.** 앱은 개발 서버 방식으로 돌렸습니다.
10. **`crop_probe.bin` 은 이 PC 에서 학습한 파일입니다.** HF 저장소와 모델 목록에 없어서 다른 PC 에서는 시각 앵커 없이 돕니다. 그 차이는 재지 않았습니다.
11. **지연.** 자동 확정 한 건에 심사 의견 글쓰기까지 8~9초가 걸립니다. 스캔은 장당 약 10초입니다.
12. **시드 37 도 같은 생성기입니다.** 값의 위치와 글꼴과 잡음이 달라질 뿐 서식은 같습니다. 처음 보는 서식을 평가한 것이 아닙니다.

## 9. 재현

```bat
:: 합성 서류 만들기와 읽기 (154장, 약 25분)
python scripts\gen_case_docs.py out\cases 11
run\windows\rocm.bat case_read out\cases out\readings

:: 추출 평가 (GPU 불필요)
cargo run -p zorogravity-core --no-default-features --example case_extract -- out\readings out\cases\truth.json

:: L1 규칙
cargo test -p zorogravity-core --no-default-features --test matrix -- --nocapture

:: L2 실제 모델, L3 OCR 포함
run\windows\rocm.bat matrix_eval out\matrix_model.json
run\windows\rocm.bat matrix_eval --readings out\readings out\matrix_ocr.json

:: 함정 사례
run\windows\rocm.bat automation_eval
```

앱 E2E 와 영상 편집은 `scripts/e2e/` 에 있습니다. 앱을 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` 와 `ZOROGRAVITY_SCANNER_DIR` 로 띄운 뒤 `l4.js` 를 돌립니다. 영상을 만들 때는 `ZOROGRAVITY_TRACE` 와 `ZOROGRAVITY_TRACE_TEXT=1` 을 함께 주고, `l4.js --record` 의 녹화와 결과, 모델 기록을 `edit_video.py` 에 넘깁니다.
